02Kernbegrippen — met een snippet uit jouw code

Per begrip: een echt stukje uit je project en waaróm het dat begrip is. Wijs tijdens het mondeling gerust naar deze regels.

Overerving kern

class Draaideur : public Deur {   // Draaideur IS-EEN Deur
public:
    void open()  override;
    void sluit() override;
    bool isLiggend() const;
};

Waarom overerving: : public Deur betekent dat Draaideur alles van Deur erft (sloten, open/sluit, status) en er eigen gedrag aan toevoegt. Hetzelfde geldt voor Schuifdeur : public Deur en SleutelSlot : public Slot.

virtual vs = 0 (pure virtual) eng

// Slot.h — pure virtual: GEEN implementatie, subklasse MOET invullen
virtual void ontgrendel(const std::string& eenSleutel) = 0;

// Deur.h — gewone virtual: Deur heeft een eigen versie, subklasse MAG overschrijven
virtual void open();

Verschil: = 0 maakt de methode pure virtual → de klasse (Slot) wordt abstract en is niet instantieerbaar; elke subklasse moet ontgrendel invullen. Een gewone virtual (Deur::open) heeft wél een basis-implementatie die een subklasse mag vervangen.

shared_ptr vs unique_ptr eng

// Deur.h — het slot wordt GEDEELD met MainWindow → shared_ptr
std::vector<std::shared_ptr<Slot>> _sloten;

// MainWindow.h — MainWindow is ENIGE eigenaar van de servo → unique_ptr
std::unique_ptr<infra::Servo> _servoVd;

Keuze-regel: shared_ptr = gedeeld bezit met referentieteller (het slot heeft twee eigenaren: Deur checkt open/sluit, MainWindow (ont)grendelt via de UI). unique_ptr = één eigenaar, niet kopieerbaar — perfect voor een servo die alleen MainWindow bezit.

Static member kern

// KaartSlot.h — één map gedeeld door ALLE KaartSlot-objecten
static std::map<std::string, IdKaart*> _idKaarten;

// KaartSlot.cpp — een static member moet je één keer definiëren
std::map<std::string, IdKaart*> KaartSlot::_idKaarten;

Waarom static: de kaartenadministratie hoort bij de klasse, niet bij één slot — elke KaartSlot ziet dezelfde kaarten (één centrale administratie, opdracht-eis). In de tests reset ik hem met wisAlleIdKaarten() in SetUp().

Exception — throw + try/catch kern

// KaartSlot.cpp — GOOIT bij een onbekende kaart-id
throw SlotException(_plaats, "geen idkaart voor " + kaartId);

// MainWindow.cpp — VANGT op en licht de rode LED op
try {
    slot->ontgrendel(invoer);
} catch (const domain::SlotException& ex) {
    _gpio->schrijfDigitaal(LED_ROOD_PIN, true);
    _kaartenbakDisplay->append("[SlotException] ...");
}

Flow: het domein (KaartSlot) gooit, de UI (MainWindow) vangt precies dáár waar ontgrendel wordt aangeroepen. SlotException erft van std::exception. Ving je hem niet op → std::terminate (crash).

Operator overloading kern

// IdKaart.cpp — combineer de toegang van twee kaarten met '+'
std::set<KaartSlot*> operator+(const IdKaart& a, const IdKaart& b) {
    std::set<KaartSlot*> result(a.toegang().begin(), a.toegang().end());
    result.insert(b.toegang().begin(), b.toegang().end());
    return result;   // set = automatisch geen duplicaten
}

Waarom: ik bepaal zelf wat kaartA + kaartB betekent: de vereniging van hun toegestane sloten. De set zorgt dat een slot dat op beide kaarten staat maar één keer voorkomt.

Lambda & functor eng

// zoek alle kaarten van "Anna" — de lambda is het filter
auto annas = KaartSlot::zoekIdKaarten(
    [](const IdKaart& k){ return k.naamEigenaar() == "Anna"; });

Uitleg: [] = capture, (const IdKaart& k) = parameter, daarna de body die true/false teruggeeft. zoekIdKaarten neemt dit als std::function<bool(const IdKaart&)> en loopt met een for over de statische map; elke kaart waarvoor de lambda true geeft, komt in het resultaat.

STL-containers kern

std::vector<std::shared_ptr<Slot>> _sloten;      // Deur: geordende lijst
std::map<std::string, IdKaart*>    _idKaarten;    // KaartSlot: sleutel→kaart
std::map<std::string, bool>        _kaartenbak;   // HerkenningsSlot: naam→mag-binnen
std::set<KaartSlot*>               result;        // operator+: uniek

Kies-regel: vector = volgorde/telbaar, map = snel opzoeken op sleutel, set = automatisch uniek. Je doorloopt ze met range-based for of algoritmen als std::find.

Aggregatie (vs compositie) eng

// Schuifdeur.h — 'heeft een' Sensor, maar bezit hem NIET
Sensor* _mijnSensor;   // nullptr toegestaan; de sensor leeft apart

// Schuifdeur.cpp — sluit weigert zolang de sensor actief is
if (_mijnSensor != nullptr && _mijnSensor->isGeactiveerd()) return;

Aggregatie: een rauwe pointer/referentie naar iets dat je niet opruimt (de sensor overleeft de deur). Compositie zou zijn: de deur máákt en bezit het object (dan een member-by-value of unique_ptr).

Polymorfisme kern

// Deur.cpp — werkt met de Slot-INTERFACE, kent het type niet
for (const auto& slot : _sloten)
    if (slot && slot->isVergrendeld())   // juiste override wordt gekozen
        return false;

Wat gebeurt er: of het slot een SleutelSlot of KaartSlot is, weet Deur niet. Via de virtual-tabel wordt automatisch de juiste isVergrendeld() aangeroepen. Dat is polymorfisme.

Unit test & TDD kern

// KaartSlot_test.cpp — test-eerst geschreven (RED), daarna groen gemaakt
TEST_F(KaartSlotTest, OntgrendelMetOnbekendeIdGooitException) {
    KaartSlot slot("vd");
    EXPECT_THROW(slot.ontgrendel("OnbekendeKaart"), domain::SlotException);
}

TDD: in de git-historie zie je per opdracht een tdd RED-commit (falende tests) en een green-commit (implementatie). 81 tests draaien met ctest; MockGpio maakt het domein testbaar zonder Pi.

04Per klasse — wat + waarschijnlijke vraag

Loop deze door tot je bij elke kaart het antwoord al ziet aankomen.

Domein — de OOPR2-kern

Slot kern

Interface met drie pure virtuals: ontgrendel, vergrendel, isVergrendeld.

V: Waarom een interface? A: Zo kent Deur alleen "een slot" — nieuwe types toevoegen zonder Deur te wijzigen.

SleutelSlot / CodeSlot kern

SleutelSlot vergelijkt strings; CodeSlot doet std::stoi en vangt invalid_argument/out_of_range.

V: Code geen getal? A: stoi gooit, ik vang het op → blijft dicht.

HerkenningsSlot kern

Kaartenbak map<string,bool>: naam → mag-binnen. Toont de bak via een Afdrukker.

V: Waarom een map? A: snel opzoeken op naam + bool voor autorisatie.

Deur kern

vector<shared_ptr<Slot>>. open() lukt alleen als álle sloten open zijn.

V: Waarom shared_ptr? A: gedeeld met MainWindow.

Schuifdeur kern

Erft van Deur, heeft een Sensor*. sluit() weigert zolang de sensor actief is.

V: Wie bezit de sensor? A: niet de deur — aggregatie.

Draaideur kern

Erft van Deur; override open/sluit om _liggend te syncen. enum class voor oriëntatie.

V: Waarom enum class? A: type-veilig i.p.v. losse ints.

IdKaart kern eng

id, naam, adres + vector<KaartSlot*>. operator+ combineert twee kaarten tot een set.

V: Waarom set? A: vereniging zonder duplicaten.

KaartSlot kern eng

Statische map van kaarten. ontgrendel checkt toegang; zoekIdKaarten filtert met lambda.

V: Waarom statisch? A: centrale administratie; test-reset in SetUp().

SlotException kern

Erft van std::exception; kaartVanBinnendringer() + plaatsVanHetSlot(). Gegooid door KaartSlot, gevangen in de UI.

V: Niet opvangen? A: std::terminate → crash.

Sensor / HallSensor SWADP

Sensor = interface; HallSensor implementeert 'm in infra. Voor OOPR2: "sensor met aan/uit-staat".

V: Waarom in infra? A: hardware-implementatie hoort in de infra-laag.

Infrastructuur — grotendeels SWADP, kort houden

IGpio SWADP

Interface met 5 methodes die pigpio verbergt (Facade).

V: Waarom? A: testen zonder Pi (mock) + library vervangbaar.

Servo kern

Vertaalt "open"/"dicht" naar een hoek via IGpio. Houdt een IGpio& vast (aggregatie).

V: Waarom referentie? A: servo's delen één GPIO-object.

MockGpio kern

Fake-IGpio in geheugen: knopdruk simuleren, waarden teruglezen, actie-log.

V: Waarom belangrijk? A: maakt de code testbaar — 20%.

PigpioGpio SWADP

Echte implementatie op de Pi; op Windows een stub.

V: Hoe bouwt het op Windows? A: via de interface + MockGpio.

05De enge vragen — antwoord ligt klaar

De vragen die je kunnen verrassen, met een modelantwoord. Lees ze hardop.

?Leg operator+ op IdKaart uit — regel voor regel.

Het is een vrije functie die twee kaarten neemt en de vereniging van hun toegang teruggeeft als set.

std::set<KaartSlot*> operator+(const IdKaart& a, const IdKaart& b) {
    std::set<KaartSlot*> result(a.toegang().begin(), a.toegang().end());
    result.insert(b.toegang().begin(), b.toegang().end());
    return result;   // set = automatisch geen duplicaten
}

"Ik vul de set met de sloten van a, voeg die van b toe; de set gooit dubbelen er vanzelf uit."

?Waarom shared_ptr en niet unique_ptr voor de sloten?

"Omdat het slot twee eigenaren heeft. Deur gebruikt het voor de open/sluit-check, en MainWindow gebruikt hetzelfde slot om via de UI te (ont)grendelen. unique_ptr staat maar één eigenaar toe; shared_ptr deelt met een referentieteller."

?Wat is het verschil tussen virtual en = 0?

"virtual = de basis heeft een implementatie die een subklasse mag overschrijven (Deur::open). = 0 = pure virtual: geen implementatie, de subklasse moet het invullen, en de klasse wordt abstract. Mijn Slot en Sensor zijn zo — echte interfaces."

?Loop de exception-flow van een foute kaart door.

1. UI roept KaartSlot::ontgrendel("XYZ") aan. 2. Id niet in de statische map → throw SlotException(plaats, "geen idkaart voor XYZ"). 3. try/catch in MainWindow vangt op. 4. Melding in het paneel + rode LED (BCM 25) aan. Niet opvangen → std::terminate.

?Heb je dit zelf geschreven? Leg klasse X uit.

Blijf rustig en redeneer hardop: naam → verantwoordelijkheid → welk concept. "Dit is X, het doet …, ik koos hier een … omdat …." Detail kwijt? Zeg wat het zou moeten doen en wijs de plek aan.

Een deur ontgrendelen & openen — vd met een kaart

1

Typ de kaart-id

Zet K001 in het invoerveld van vd. (Kaart K001 = Anna bestaat standaard al, met toegang tot vd én d1.)

2

Klik "Ontgrendel"

De KaartSlot zoekt K001 in de statische map en checkt of Anna toegang heeft tot vd → slot open. Status wordt groen en de deurlijn wordt zwart.

3

Klik de deurknop "vd (schuifdeur)"

De deur opent (mag, want alle sloten open) → de servo draait en de lijn verdwijnt. Nog eens klikken = sluiten (dat vergrendelt de sloten meteen weer).

SlotException tonen (opdracht 6): typ een onbekende id zoals XYZ in het vd-veld en klik Ontgrendel. → De KaartSlot gooit een SlotException, de rode LED gaat aan en in het output-paneel verschijnt [SlotException] plaats 'vd' - id: geen idkaart voor XYZ.

Moet ik een kaart aanmaken? (opdracht 5)

Niet per se — K001 (Anna) bestaat al. Maar zélf een kaart maken laat opdracht 5 mooi zien. Rechterkolom "IdKaart-beheer (vd + d1)":

1

Vul de kaartgegevens

Kaart-id (bv. K002), Naam, Adres. Vink Toegang vd en/of Toegang d1 aan (standaard aan).

2

Klik "+ Maak IdKaart"

De kaart komt in de statische map (paneel: [OK] kaart 'K002' aangemaakt) en krijgt toegang volgens de vinkjes.

3

Gebruik de nieuwe kaart

Typ nu K002 bij vd of d1 → Ontgrendel → open. En laat de STL/lambda zien: Zoek (naam) filtert met een lambda, Toon alle print alle kaarten, Verwijder haalt een kaart op id weg.

d2 heeft TWEE sloten (code + herkenning)

Een deur opent pas als álle sloten open zijn. Voor d2 moet je dus twee keer ontgrendelen:

1

Ontgrendel de code

Typ 5678 in het d2-veld → Ontgrendel (opent de CodeSlot).

2

Ontgrendel de herkenning

Typ Anna → Ontgrendel (opent de HerkenningsSlot — Anna mag binnen, Bert is geblokkeerd). Nu zijn beide sloten open → klik d2 → opent.

Kaartenbak d2 beheren: typ een naam in het d2-veld en klik + TOEGANG (mag binnen) of + GEBLOK. (geblokkeerd). Toon kaartenbak print de hele lijst in het paneel.

Halsensor (veiligheid, opdracht 1)

Klik halsensor toggle → de cirkel wordt blauw (geactiveerd). Probeer nu vd te sluiten: dat weigert zolang de sensor actief is (alsof er iemand in de deur staat). Toggle terug naar geel → vd sluit weer.

Zo hoort het "volgens de opdracht": deuren gaan open/dicht (schuifdeur schuift, draaideur draait 90°), een deur opent alleen als alle sloten open zijn (opdr. 2–3), naam-herkenning (opdr. 4), kaart-id's met toegangsrechten (opdr. 5), en een foute kaart geeft een exception + rode LED (opdr. 6). De halsensor blokkeert het sluiten van de schuifdeur (opdr. 1).

⚡ Servo's uit de Pi — één tegelijk

Jouw SG90's hangen direct aan de Pi-5V (pin 2/4). Klein genoeg voor de demo, maar beweeg ze niet alle drie tegelijk. Flikkert het beeld of reset de Pi? Dan trekken ze te veel stroom — beweeg rustiger, of gebruik alsnog een externe 5V-bron.

Deel de 5V- en GND-pin

Er zijn maar twee 5V-pinnen (2 en 4). Sluit de drie rode servo-draden samen op 5V aan (bijv. via een breadboard-rail) en de drie bruine op een GND-pin.

↑ Knoppen = pull-up

Knop tussen GPIO en GND; de code zet interne pull-up aan, dus ingedrukt = LAAG. Geen weerstand nodig.

3V3 max op GPIO

Nooit rechtstreeks 5V op een signaalpin — GPIO-ingangen verdragen max 3,3V. Knoppen schakelen naar GND, dus dat zit goed.
